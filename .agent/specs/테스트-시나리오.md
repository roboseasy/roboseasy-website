# 테스트 시나리오 — RoboSEasy Backend API

`.agent/specs/` 명세서(API·기능·요구사항)와 `src/server/` 실제 구현 기준의 QA 테스트 시나리오.
정상 흐름(happy path) + 예외/경계/권한/멱등을 모두 포함한다. 회귀 테스트 기준 문서로 사용.

- **대상**: `/api/v1/*` (Hono, `src/server/routes/`) — 응답은 JSON, 인증 필요 API는 세션 쿠키 검사
- **표기**: 각 케이스는 `Given`(전제) / `When`(실행) / `Then`(기대 — 상태코드 + 부수효과)
- **우선순위**: 상 / 중 / 하 (명세서 우선순위 계승)
- **유형**: 정상 / 예외
- 관련 명세: [API 명세서.csv](API%20명세서.csv) · [기능 명세서.csv](기능%20명세서.csv) · 정책 근거는 [../backend.md](../backend.md)

## 통합 시나리오 (E2E — 여러 API 연쇄)

| ID | 제목 | 흐름 |
|---|---|---|
| E2E-01 | 가입→로그인→주문→결제 | signup → (이메일 확인) → login → 장바구니 추가 → `POST /orders`(PENDING) → 토스 위젯 → `POST /payments/confirm`(PAID) → 장바구니에서 품목 제거 확인 → `GET /orders`에 노출 |
| E2E-02 | 결제 실패 복귀 정리 | 주문 생성(PENDING) → 결제 실패 → failUrl → `cancel?mode=abandon` → payments 없으면 주문 삭제 / 있으면 재결제 유지 |
| E2E-03 | 주문 후 취소·환불 | 결제 완료(PAID) → `cancel` → 토스 취소 → CANCELLED + 실환불 확인 |
| E2E-04 | 관리자 배송 처리 | admin login → `GET /admin/orders`(PAID) → `PATCH …/delivery`(SHIPPING, 운송장) → 유저 `GET /orders`에서 취소 시 400 확인 |
| E2E-05 | 주문 이력 회원 탈퇴 | 주문(DELIVERED) 보유 유저 → `DELETE /users/me` → 익명화 경로(profiles 익명화·withdrawn_at·거래기록 보존·cart/dibs 파기·문의 익명화) |
| E2E-06 | RLS 격리 | 유저 A 로그인 → 유저 B의 주문/장바구니/문의 id로 조회·수정 시도 → 전부 404/빈 배열 |
| E2E-07 | PENDING 자동 정리 | 24h 경과 PENDING → 매시간 pg_cron `cleanup_pending_orders()` → payments 없으면 DELETE, 있으면 CANCELLED |
